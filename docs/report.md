# Project Report: Decentralized EHR Authenticity and Consent Audit

## Research question and scope

This project asks: **on one local machine, what integrity, consent, latency, throughput, and storage behavior does a blockchain-backed EHR audit prototype show compared with the same API workflow using an in-process metadata store?** It is an educational cybersecurity/systems study of record authenticity and authorization mechanisms. It does not evaluate diagnosis, treatment, prediction, clinical correctness, or patient outcomes.

A ledger can make a committed sequence of events harder to silently rewrite for parties who share its governance. A ledger cannot establish that a medical value was entered correctly, identify who is actually using a device, or prevent a recipient from copying plaintext. This prototype makes those boundaries explicit while providing an executable local system and a matched, reproducible benchmark.

## System design

The Node.js API deploys `EHRAudit.sol` to a fresh Hardhat Network process. The application stores an AES-256-GCM envelope on the local filesystem and places record metadata and content commitments on-chain. The patient role can grant doctor/insurer access for a bounded period and revoke it. An access request checks consent, verifies the encrypted-envelope hash, authenticates/decrypts the envelope, recomputes a salted plaintext commitment, and only then requests an `AccessReported` event.

The contract stores no record text, but on-chain IDs, wallet addresses, pseudonyms, commitments, consent timing, and access events remain public and linkable. A patient pseudonym is a keyed, deterministic identifier, not anonymity. `AccessReported` is a caller assertion: the EVM contract cannot independently inspect off-chain bytes. The default API and walkthrough accept fabricated records only. Simulated role headers, local test signers, ephemeral chain state, and the temporary file store are development conveniences, not authentication or production storage.

## Data and benchmark

The default tests and benchmark use fabricated fixtures. An optional local-only importer reads the public, de-identified [MIMIC-IV Clinical Database Demo release 2.2](https://physionet.org/content/mimic-iv-demo/2.2/), a 100-patient subset that excludes free-text notes. The source is licensed under the [Open Data Commons Open Database License v1.0 (ODbL-1.0)](https://registry.opendata.aws/mimic-iv-demo/); attribution, field selection, access details, and reproducible commands are in the [benchmark protocol](benchmark-method.md).

The benchmark joins source rows in memory, selects the first admission encountered for each subject and its lowest-sequence diagnosis, generates a random demo alias, and does not copy source identifiers into a record. It runs the same application API, encrypted local file store, consent checks, and integrity checks against two backends: the local EVM contract and an in-process map without a blockchain. Each record is tested for denial before grant, successful grant, integrity verification, authorized retrieval, ciphertext modification rejection, revocation, and denial after revocation. Temporary encrypted files and chain processes are removed at exit. The report artifact is aggregate-only; source data, IDs, row-level results, and keys must not be committed.

The benchmark measures per-operation latency, serial records per second, encrypted-envelope size, local transaction gas, and documented storage estimates. Its deterministic bootstrap interval describes the sample median's variation among operations in this one run. It is not an inferential interval across hospitals, deployments, machines, or patient populations. The EVM is local and has no dollar fees; storage estimates exclude trie/block overhead, event logs, and hardware-specific allocation. The detailed methodology identifies workflow-order and warm-up limitations and recommends repeated counterbalanced runs for stronger system-level conclusions.

## Evidence and interpretation

The committed aggregate result is [`docs/results/mimic-iv-demo-2.2.json`](results/mimic-iv-demo-2.2.json). It records the dataset release, sample count, runtime environment, measured behavior, operation summaries, gas observations, and storage-size estimates without row-level identifiers. Re-run it by following the command sequence in [`docs/benchmark-method.md`](benchmark-method.md); latency and throughput will vary with runtime, machine load, and filesystem state.

This run processed **100 demo-patient records** on Node.js 24.19.0/Linux x64. The chain path granted and revoked all 100 requests, denied all 100 pre-grant and 100 post-revocation reads, and rejected all 100 ciphertext-tamper trials; the no-chain path had the same 100/100 outcomes. Its end-to-end serial rate was **2.320 records/s**, compared with **55.366 records/s** for the simpler no-blockchain baseline. The chain-backed median create latency was **56.881 ms** (bootstrap 95% interval for the sample median: **51.539–60.976 ms**) versus **2.771 ms** (**2.706–2.893 ms**) for the baseline. Median integrity verification was **73.437 ms** (**73.177–73.788 ms**) versus **2.375 ms** (**2.347–2.457 ms**). These local measurements include application/API work; the baseline has an in-process grant map and no signatures, consensus, or chain transaction, so its performance is not a like-for-like distributed deployment comparison.

Observed median EVM gas was **137,028** for record creation, **51,667** for a grant, **30,611** for verification and access reports, and **29,029** for revocation. Encrypted envelopes averaged **712.7 bytes** (95th percentile **747 bytes**) in both paths. The Solidity record-state estimate is **160 bytes per record**, plus **32 bytes while a grant is active**; the baseline's approximate serialized metadata entry was **380 bytes**. These are local execution and storage estimates—not dollar fees or whole-chain storage measurements. The bootstrap intervals summarize variability across operations in this one serial run, not uncertainty across hardware, deployments, or patients.

The tests separately exercise the API's synthetic-only default, the explicitly gated local benchmark path, consent denial and revocation, ciphertext tamper detection, transaction failures, pseudonym derivation, cryptographic validation, CSV parsing, and output privacy. Those are executable regressions, not an independent security audit. The results support narrow claims about the tested implementation on a local machine only; they do not establish real-world decentralization, privacy against all observers, regulatory compliance, or operational fitness.

## Limits and next steps

This prototype has no independently governed validators, real identity proofing, patient-controlled wallet, key lifecycle service, durable storage, recovery design, purpose-bound consent, standards-based interoperability, operational threat monitoring, or external security review. The demo role header is impersonable, a compromised process/master key can disclose records, prior authorized plaintext cannot be recalled, and immutable ledger metadata may be linkable. De-identification and date shifting do not eliminate all re-identification risk; the public demo is small and not representative of a general hospital population.

A stronger research extension would repeat the matched benchmark with counterbalanced workflow order on recorded hardware, add carefully separated persistence/consensus comparisons, publish only aggregate results, and obtain independent contract/API review. Any broader dataset use would require direct compliance with the publisher's terms and the user's own authorization. This artifact must not be used for clinical, coverage, reimbursement, or operational decisions.
